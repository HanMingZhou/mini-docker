# 一、 为什么 PID 1 “永远活着”？
在 Linux 系统中，PID（进程标识符）为 1 的进程是极其特殊的。早期系统中它叫 init，在现代 Linux发行版（如 Ubuntu, CentOS 等）中，它通常是 systemd。
它之所以“永远活着”，是因为它绑定了操作系统的生死：
1. 它是所有用户态进程的“老祖宗”
   当 Linux 内核启动完毕后，内核会手动拉起第一个用户态进程，并强行给它分配 PID 1。系统里之后运行的所有进程（包括 SSH、Nginx、Docker 甚至你敲进去的每个命令），本质上都是 PID 1 的子孙进程（通过 fork() 繁衍出来）。

2. 如果 PID 1 死了，系统直接内核崩溃（Kernel Panic）
   Linux 内核在底层是强依赖 PID 1 的。如果因为任何原因（比如段错误崩溃，或者被误杀了），导致 PID 1 进程退出，Linux 内核会认为“用户态的根基没了，系统无法继续运转”，然后立刻抛出 Kernel Panic（内核恐慌） 错误，强行让整台机器死机或重启。
   报错信息通常长这样：Kernel panic - not syncing: Attempted to kill init!
   结论：只要这台服务器（或节点）还在正常开机运行，PID 1 就绝对活着。

3. 它是系统的“孤儿院院长”和“收尸人”
   在 Linux 里，如果一个父进程先于子进程死掉了，子进程就会变成“孤儿进程”。内核会自动把所有孤儿进程过继给 PID 1。PID 1 负责在这些孤儿死后，回收它们的资源（防止出现大量“僵尸进程”占满系统）。这个沉重的责任要求它必须永远在线。

# 二、 为什么这段代码要用 PID: 1 和 /proc/1/ns/net？
这段代码处理的是 Kubernetes 中配置了 hostNetwork: true 的 Pod（即主机网络模式的 Pod，这类 Pod 不使用容器虚拟网络，而是直接共享宿主机的网络网卡和 IP）。
要理解代码的巧妙之处，需要对比一下普通的 Pod：
普通 Pod：需要 pause 进程来“占坑”
对于普通的 Pod，容器运行时（如 containerd）会先启动一个叫 pause 的极小容器（就是大名鼎鼎的 Infra 容器）。
pause 进程唯一的作用就是活着，并且发呆。
为什么要它活着？因为 Linux 的网络命名空间（Network Namespace）是跟进程绑定的。只要 pause 进程活着，它的 /proc/<pause_pid>/ns/net 文件就存在，这个 Pod 的专属虚拟网络（veth、IP、路由规则）就不会消失。其他的业务容器启动后，只需要“加入”这个 pause 进程的网络命名空间即可。

hostNetwork Pod：不需要占坑，直接“傍大款”
当 Pod 设置了 hostNetwork: true 时，它不需要创建专属的虚拟网络，它需要的是宿主机本身的物理网络。
这就带来了一个问题：在容器运行时的代码逻辑里，Sandbox（沙箱）对象总是需要记录一个 PID 和一个 NetnsPath（网络命名空间路径），以便后续的业务容器知道该加入哪个网络。

既然需要宿主机的网络，那该用宿主机上哪个进程的 PID 来代表宿主机网络呢？
用 Nginx 的 PID？不行，Nginx 可能会重启。
用 Kubelet 的 PID？不行，Kubelet 也可能会挂掉重启，PID 会变。
唯一的完美答案就是 PID 1。
因为：
PID 1 的网络命名空间 /proc/1/ns/net，就是最原汁原味的宿主机根网络命名空间（Root Network Namespace）。
正如我们上面论证的，PID 1 永远活着。以它作为锚点（Anchor），永远不用担心这个文件路径失效，永远不需要像普通 Pod 那样单独拉起一个 pause 进程去维持网络空间的生命周期。

总结
这段代码中的 // PID 1 (systemd) 永远活着 是一种非常极客且优雅的底层实现方式：既然你想和宿主机同呼吸共命运（hostNetwork），那我就直接把你的网络锚点绑在宿主机最坚固的基石（PID 1）上。 这不仅省去了一个多余的 pause 进程，而且在逻辑上无懈可击。
